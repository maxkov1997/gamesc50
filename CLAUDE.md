# CLAUDE.md

## Проект
Карточный автобатлер один на один. В подготовке игрок тратит ману на карты из руки: выставляет и усиливает существ, накладывает чары, прячет секреты. Потом бой идёт сам. Референсы: Become the Moon — подготовка, колода, мана; Hearthstone Battlegrounds — автобой.

Сейчас делаем только ядро одного матча. Все правила — в `docs/GDD.md`, это источник истины. Ничего из раздела 2 GDD («Вне рамок») не делаем.

## Стек
- Движок и язык: C# / .NET 8. Ядро, данные, бот и симулятор — обычные библиотеки .NET без движка; интерфейс (M5) — Godot 4 (.NET), подключает ядро как проект.
- Тестовый фреймворк: xUnit (`tests/Game.Tests.csproj`).
- Если строка «Движок и язык» не заполнена — спроси пользователя до начала работы. Сам не выбирай.

## Порядок работы
1. Перед задачей прочитай разделы GDD, на которые она опирается. Глоссарий (раздел 0) и константы (раздел 3) — всегда.
2. Иди по этапам раздела 14: M0 → M1 → … → M5. Новый этап начинай, только когда зелёные все тесты текущего и прошлых этапов.
3. Каждый тест-кейс раздела 13 — отдельный автотест, имя начинается с номера: `T05_taunt`, `T29a_mourner_in_combat`. Сначала тест, потом код.
4. Тест-кейс — часть спецификации. Не меняй его ожидания, чтобы он прошёл. Если тест противоречит правилам GDD — остановись и опиши противоречие пользователю.
5. Если GDD чего-то не покрывает: выбери самый простой вариант, который ему не противоречит, пометь место в коде комментарием `GDD-QUESTION:` и запиши вопрос в `docs/QUESTIONS.md`. Варианты «по умолчанию» из раздела 15 уже решены — альтернативы не реализуй.
6. GDD меняется только с согласия пользователя. Если правило мешает — предложи правку текста, а не обходной путь в коде.
7. После каждого этапа — короткий отчёт пользователю: что сделано, какие тесты зелёные, что появилось в `docs/QUESTIONS.md`.

## Правила кода
Нарушение любого пункта — баг.
- **Детерминизм.** Вся случайность — через RNG ядра с seed (раздел 10). Нельзя: системный рандом, время, float в правилах, итерация по неупорядоченным коллекциям.
- **Карты — это данные.** Поведение карт задаётся только в `content/`. В правилах нет проверок конкретных id карт. Новая механика = операция, селектор или триггер в реестре + тест.
- **Ядро изолировано.** `core` не зависит от движка, интерфейса, файловой системы и сети; данные приходят через загрузчик `content`.
- **Бой — чистая функция** от снимка и seed. Интерфейс только проигрывает лог боя (12.3) и на исход не влияет.
- **Стороны изолированы в подготовке** (5.6).
- **Никаких магических чисел.** Константы — из конфига (раздел 3), тексты для игрока — из данных.

## Структура (рекомендуемая)

| Путь | Что |
|---|---|
| `docs/GDD.md` | Правила |
| `docs/QUESTIONS.md` | Вопросы, возникшие по ходу работы |
| `content/config.json` | Константы раздела 3 |
| `content/cards.json`, `content/decks/` | Карты и тестовые колоды |
| `content/src/` | Загрузчик и валидатор данных (модуль `content`) |
| `core/` | Состояние, правила, очередь, бой, RNG, лог |

| `view/` | Интерфейс (этап M5) |
| `tests/` | Автотесты T-xx и тесты карт |

## Команды
- тесты: `dotnet test` (из корня репозитория; решение `Game.sln`)
- симулятор: `dotnet run --project sim -c Release -- --decks pack,bones --matches 1000 --seed 1` — краткий текст в stdout, JSON в `--out <файл>` (без него — тоже в stdout); `--decks all` — все пары колод, включая зеркала; код выхода 1, если были исключения, `limit` или `warning`
- отчёт M4 по всем парам: `docs/sim/m4-all-pairs.json` и `.txt`

## Этап готов, когда
- зелёные все тест-кейсы этапа из раздела 14 и всех прошлых этапов;
- в тестах нет исключений и событий `warning`;
- отчёт пользователю отправлен.

## Язык
Код, идентификаторы и имена тестов — по-английски, как в GDD. Общение с пользователем, документы и комментарии — по-русски.
